# Device and protocol quirks

Known problems in existing implementations (AOSP adb, libmtp, …) and device behavior measured directly. Code comments refer to entries by ID, e.g. `QUIRKS A12`.
IDs never change. A removed entry leaves its number unused.

Handling: **Fixed** = applied as a protocol fact · **Verified** = tested on the device at connect time, then decided · **Defensive** = always worked around, without testing · **Restricted** = blocked, with guidance to the user · **Unverified** = not yet confirmed

## A. ADB

| ID | Behavior | Source | Handling |
|---|---|---|---|
| A1 | `LIS2`/`STA2` are available only when the device reports the `ls_v2`/`stat_v2` feature | AOSP adb | Verified: checked with `host-serial:<s>:features`; without them, v1 `LIST`/`STAT` |
| A2 | v1 `LIST`/`STAT` carry size and time as 32-bit values → anything 4 GB or larger is truncated (5 GB → about 705 MB). Devices without `ls_v2` are roughly Android 7 and older | AOSP file_sync_protocol | Fixed: `capabilities.exactLargeSizes = false`; sizes are compared on their low 32 bits. Listings show the truncated value as is |
| A3 | The `DONE` that ends a listing arrives with the same size as a dent struct | AOSP `file_sync_service.cpp` | Fixed: read a header's worth of bytes and stop |
| A4 | `LIST` on a directory that does not exist returns an empty list with no error | AOSP adb | Fixed: use `STA2` to check existence when it matters |
| A5 | A sync request path is at most 1024 bytes; a `DATA` chunk is at most 64 KB | AOSP adb | Fixed: error when exceeded |
| A6 | `.` and `..` are included in listings | readdir | Fixed: filtered out |
| A7 | v1 `LIST` silently omits entries whose lstat fails. v2 sends them with `error` set (raw errno). A failed `STA2` is also not a FAIL but an `error` field | AOSP `do_list`, `do_stat_v2` | Fixed: error≠0 → an entry without size and time; for stat, "does not exist" / "permission denied" |
| A8 | Sync commands on one connection are processed in order → several requests can be sent ahead and the replies still come back in order | AOSP `file_sync_client.cpp` | Fixed: the queue hands small files over in batches of 64 (or 8 MB); within a batch up to 32 RECVs are sent ahead (refilled when fewer than 16 are outstanding — pipelining). See the appendix table |
| A9 | When a RECV fails (FAIL), adbd closes that sync connection → the requests already sent ahead are lost too | AOSP file_sync_service | Fixed: only the failed file fails; the remaining files continue on a new connection |
| A10 | toybox `mv -n` does **nothing and succeeds (0)** when the target exists. `rm -rf` returns 0 for a path that does not exist. `[ -e ]` does not see a dangling symbolic link | Measured (toybox 0.8.12) | Fixed: rename checks `[ -e ] \|\| [ -L ]` and runs `mv -n` within a single shell command. Delete runs only after the path is validated (no `/`, no `..`) |
| A11 | Whether a shell command succeeded cannot be told from the exec output alone | adb `exec:` | Fixed: `{ cmd; } 2>&1; echo __XFER_RC=$?` returns the exit code together with the messages |
| A12 | SEND v1: `"path,mode"` → DATA → `DONE`+mtime → OKAY/FAIL. When an upload is interrupted, adbd deletes the incomplete file **a little later** → uploading again under the same name right away gets the new file deleted too | AOSP `file_sync_client.cpp`, measured (Lenovo Tab P11) | Fixed: send under a hidden temporary name `.name.<unique>.xfer-part` and replace with `mv -f` when done (the original stays intact until the end). Dates are preserved. Writing directly (a setting) sends under the original name, so on failure the app waits until adbd has deleted that file (up to 3 s) before returning the error. adbd deletes an existing file of the same name as soon as it starts receiving (the unlink in `send_impl`) → when replacements are also written directly, an interrupted transfer leaves no way to recover the original |
| A13 | `tar` is part of toybox from Android 9 on. The stream can be cut off before its end marker | AOSP toybox, defensive | Defensive: "Bundle small files when transferring" (off by default). If tar is missing, or for files missing from the stream, fall back to the normal method. If a header checksum does not match (the stream is out of step), the remaining files use the normal method. The checksum is an unsigned byte sum: on toybox 0.8.3 (Lenovo Tab P11) Korean and emoji names match it that way too (a signed sum differs). See the appendix table |
| A14 | `host:connect` answers OKAY on both success and failure; the result comes as text (`connected to …`, `already connected to …`, `failed to connect …`). `host:pair` on failure sends `OKAY` `FAIL` text, but **on success sends the text right after `OKAY`** (`Successfully paired to … [guid=adb-SERIAL-…]`). Always expecting a second status reads success as failure | Measured (adb 36.0.2) | Fixed: only `connected to` / `already connected to` count as success. For pair, the 4 bytes after OKAY are inspected to tell FAIL, OKAY or a length, and success requires text starting with `Successfully` |
| A15 | With wireless debugging on, the port changes every time, and macOS adb's mDNS sometimes does not see the new port | Measured (Lenovo Tab P11) | Workaround: when USB is plugged in, read it from the phone directly (Wi-Fi address + the port uid 2000 (adbd) listens on in `/proc/net/tcp*`, excluding 5555). mDNS is secondary |
| A16 | A phone that has authorized this Mac over USB connects over wireless debugging without pairing (same key) | Measured (Lenovo Tab P11) | Fixed: phones already authorized connect over Wi-Fi automatically. Pairing (QR/code) is only for phones not seen before |
| A17 | `host:connect` (= `adb connect`) waits for the system TCP timeout (75 s) when the other side does not answer. Happens on Wi-Fi networks that block traffic between devices (same subnet, yet neither ping nor the port answers) | Measured (Lenovo Tab P11, corporate Wi-Fi) | Workaround: a 3 s TCP check before connecting (`tcpReachable`); if unreachable for 15 s, tell the user it cannot be reached |
| A18 | After pairing completes and the phone closes its pairing screen, the pairing service stays in adb's mDNS list (`host:mdns:services`) for a few more seconds. Pairing again to that address gets Connection refused | Measured (Galaxy S23: stays 1–2 s after pairing; has been seen still present 15 and 17 s later) | Workaround: QR pairing tries each advertised address only once. Scanning again makes the phone open a new address, which is then tried |
| A19 | The sync protocol (`RECV`) sends a file only from start to end. There is no request to read at an offset | AOSP adb `file_sync_protocol.h` | Workaround: ranges use `exec:dd iflag=skip_bytes,count_bytes` (toybox; byte-exact on Lenovo Tab P11 Android 11, 1 MB in 0.17 s). Older `dd` (toolbox) may lack `iflag`, so at connect time the app reads 2 bytes with `echo abcd \| dd …`; if that fails, `readsRanges = false` (open in an app instead of playing; previews read the whole file). Receiving fewer bytes than requested is treated as a failure |
| A20 | The media library's `_data` (`content query … images/media`) is `/storage/emulated/N/…`, but the real path of `/sdcard` (`realpath`) can, depending on the device, come out as an internal mount (`/mnt/runtime/*/emulated/N/…`, `/mnt/user/N/primary/…`, `/data/media/N/…`) (reported for some Android 10 devices, unconfirmed). The `content` tool may also be blocked or return errors | Raised in code review (unconfirmed). On Galaxy S23 the `realpath` result matches directly | Workaround: those paths are rewritten to `/storage/emulated/N/…` before querying. If the result is neither "Row:" nor "No result found", the app stops asking for the rest of that connection (previews without thumbnails) and logs the first few lines (`adb` category). Devices that show this should be recorded here with their output |

## S. Android storage

| ID | Behavior | Source | Handling |
|---|---|---|---|
| S1 | `/sdcard` is a symbolic link | Android | Fixed: listings follow the link. Link entries are shown as `symlink` |
| S2 | `/sdcard` (= `/storage/emulated/0`) is FUSE (MediaProvider), so listing large folders is slow. Galaxy Z Flip5 `DCIM/Camera` with 7,300 items ≈ 1.4–6 s (same for `adb ls` and shell `ls`). The bypass paths (`/mnt/pass_through`, `/data/media`) are not accessible with shell permissions | Measured (Galaxy Z Flip5, Android 16) | Fixed: show the first batch immediately (80–270 ms) |
| S3 | Names containing `" : * ? < > \| \` are refused at creation (Operation not permitted). FAT compatibility rules. Both ADB and MTP | Measured (Lenovo Tab P11) | Restricted: `FileNames.isAllowed` rejects them up front in upload, new folder, rename and the batch-rename preview |
| S4 | The media DB (`content query --uri content://media/external/file`, folder selected with `relative_path`) returns every item including hidden files and folders, but files just created from the shell (adb) have **NULL size and date** (folders have only a date). The `content` command alone takes about 0.85 s to start | Measured (Lenovo Tab P11, Android 11, 5,000-item folder: DB 1.43 s, full `adb ls` 1.8 s, shell `ls` 0.9–1.4 s) | Not used: not faster, and size and date cannot be trusted. Showing the first batch immediately (S2) is enough |
| S5 | Files by Google on Android 11 cannot extract Zip64 entries: it creates the folders inside the archive, but the files are empty and it reports "unknown error". A zip with the same structure without Zip64, and a plain zip, extract fine (compared with three archives of the same content). On Android 14 all three extract, even though its Files app version is lower → the difference appears to be the OS zip library, not the app. On both devices extracted files get the extraction time as their date, not the zip's DOS date | Measured (Lenovo Tab P11 Android 11, Files 1.13003: fails; Teclast Android 14, Files 1.7223: succeeds) | Inform: when sending a ZIP over 4 GB, the upload window says some file managers may not extract it (the app cannot know the phone's file manager, so it does not block) |
| S6 | Moving or renaming a folder inside `/sdcard` takes time proportional to the number of files in it (an operation the underlying filesystem does in one step). Galaxy S23: `mv` of a 1-file folder 0.2 s; renaming an 8,000-file folder in place 5.9 s, moving it to another folder 36 s (app queue, ADB). MTP MoveObject also takes 14 s. MediaProvider appears to update its record for each item inside (unconfirmed) | Measured (Galaxy S23) | Restricted: there is no way around FUSE without root. The app sends a single command and waits for it to finish |
| S7 | Storage is **case-insensitive and Unicode-normalization-insensitive** in names (`NOTE.txt` where `note.txt` exists, or the same Korean name written in NFC and NFD, is one file). The MTP server, however, distinguishes names: sending `NOTE.txt` as a new file and renaming it (or writing it directly) **changes the existing file's content**, and the listing shows two entries. The ADB shell (`[ -e ]`) sees them as the same file | Measured (Lenovo Tab P11, MTP) | Defensive: every "does this name exist" check against a device folder compares with `FolderNames` (ignoring case and normalization) — placement planning (`DeviceFolderPlacer`), "keep both" names, the MTP path cache and existence checks. On MTP, if a name planned as a new file is in the path cache, it is reported as "already exists" instead of being overwritten (devtest "names differing only in case"). Case-only renames: ADB `mv` reports success (0) but leaves the name unchanged; an MTP rename also reports success but the stored name stays (only the listing changes) → the app renames twice via a hidden name (`WorkNames.moving`) (both confirmed on Lenovo Tab P11, covered by devtest) |

## M. MTP (all Android)

| ID | Behavior | Source | Handling |
|---|---|---|---|
| M1 | Android claims GetObjectPropList (`0x9805`) support but misbehaves. Galaxy S23: requesting "all properties" without a format (`format=0`) fails with `0xA801` in folders containing JPEGs. Specifying JPEG as the format succeeds. Property groups give `0xA807`; `property=0,group=0` gives `0x2006`. One property at a time succeeds in every folder (176/176 match GetObjectInfo). libmtp also classifies the all-objects bulk request (`0xFFFFFFFF`) as broken | libmtp `DEVICE_FLAGS_ANDROID_BUGS`, `BROKEN_MTPGETOBJPROPLIST_ALL`, measured (Galaxy S23) | Fixed: request per property, per folder (depth 1) (name and format → size and date). Compare against GetObjectHandles and fill in only the missing objects with GetObjectInfo. No device has been seen where the name request itself fails (there is no fallback for that) |
| M2 | Property cost varies widely. Name and format are instant (7,300 items in 70 ms); size and date are slow and erratic (active Camera folder with 7,300 items 2–3 s, 18.5 s on a cold first request). A bulk size request cannot be interrupted (MTP is a single channel), so other folder listings queue behind it. Per-file GetObjectInfo takes 2–7 ms each | Measured (Galaxy Z Flip5) | Fixed: show names first. For folders over 500 items, sizes and dates come in slices of about 0.15 s worth (GetObjectInfo), visible rows first. Browse requests go ahead between slices. When selected files have names but no sizes yet: use what browsing already fetched; if still being fetched, move those files to the front and wait. If the remainder is 500 or more, or a quarter of the folder or more, fetch the whole folder in bulk; otherwise one by one. Transfer planning (walking whole folders) always uses two bulk requests per folder, regardless of size (slices take one request per file, several times slower overall; browsing waits meanwhile) |
| M3 | Files over 4 GB have `0xFFFFFFFF` as the ObjectInfo size | MTP spec, go-mtpfs, measured (Lenovo Tab P11, 5 GB file) | Fixed: re-read with the ObjectSize (64-bit) property. Every path that turns an ObjectInfo into an entry (storage top-level listing, filling in missing entries, single-entry lookup, size/date filling) goes through one function. Without that correction a listing reports 4 GB−1 as a final size, and a download of it completes truncated |
| M4 | Some devices return wrong ObjectInfo values | libmtp `PROPLIST_OVERRIDES_OI` | Defensive: small folders use PropList values. Sizes and dates for folders over 500 items come from ObjectInfo (because of M2). No such device has been seen yet |
| M5 | MTP dates can arrive without a time zone. On Galaxy S23 they match the ADB mtime (phone and Mac both in KST) | Measured | Unverified: phone and Mac in different time zones |
| M6 | Devices that respond slowly | libmtp `LONG_TIMEOUT` | Defensive: long timeouts (listing 120 s, read 60 s, write commands checked after 4 s) |
| M7 | **The Device Reset class request (0x66) is harmful**: used right after cleaning up ptpcamerad, it hangs for 30–40 s in 2 of 3 attempts (without it, 3/3 fine at 0.27 s). libmtp's `FORCE_RESET_ON_CLOSE` is not used for the same reason | Measured (Galaxy Z Flip5), libmtp | Defensive: never reset. Responses left behind by a previous client are read and discarded until the pipe is quiet. If the first OpenSession is not accepted, wait and retry (15 s, or 90 s if ptpcamerad was cleaned up) |
| M8 | **PTP Cancel Request (0x64) is unreliable**: cancelling during a large file read → once it recovered after 1.2 s, once the MTP server hung and every command timed out. Clearing the stall or reapplying the same mode does not recover it; only turning the USB function off and on does | Measured (Galaxy S23) | Defensive: never send cancel requests. Downloads stop between 8 MB chunks; listings wait to finish and the result is discarded. If MTP hangs and ADB is available, "Restart the Device’s File Transfer" (resets the USB function) |
| M9 | **SendObject: a USB transfer that is not a multiple of the packet size is treated as the end of the data phase** → sending `header+1MB` stored only 1 MB and no response came | Measured (Lenovo Tab P11) | Fixed: every transfer but the last is a packet multiple (first transfer = 12 B header + 1 MB−12 B); if the end falls on a packet multiple, send a zero-length packet. Covered by boundary-size tests |
| M10 | Some devices hang on a GetPartialObject response whose last packet is exactly full (Samsung) | libmtp `SAMSUNG_OFFSET_BUG` | Defensive: if the last chunk of a file ends on a packet boundary, request 1 byte less |
| M11 | If the sender disappears during the SendObject data phase (app force-quit), the phone keeps waiting for the remaining bytes and writes the next connection's commands as file data → "no response". The first connection in that state fails after about 30 s, but releasing and reopening the interface connects immediately (same for waits of 0–20 s) | Measured (Lenovo Tab P11) | Workaround: on "no response" at connect time, reopen the interface once and retry (recovers automatically, without ADB). Uploads go under a hidden temporary name so the original is safe; leftover temporary files are removed when the queue plans that folder (`tidyLeftovers`) |
| M12 | Right after another process dies mid-MTP-transfer, opening the interface briefly fails with "Failed to create IOUSBHostInterface" | Measured (Lenovo Tab P11, as the second device) | Defensive: retry every 0.5 s for up to 6 s. The retry catches the `MtpError.usb` that MtpSession wraps (otherwise it never fires, and force-quit tests fail intermittently on Teclast). Busy retries are counted separately |
| M13 | MTP has no overwrite (renaming to an existing name and SendObjectInfo with an existing name are refused, M20) | MTP spec | Fixed: an upload is sent in full under a hidden temporary name (`.xfer-part-<unique>`, independent of the original name so it never hits the length limit) and only **after** it is confirmed is the original being replaced deleted and the new file renamed. If the connection drops in that gap (tens of ms), the new file stays under the temporary name; copying again deletes that temporary file at planning time and sends the file again from the start. On-device copy/move (Copy/MoveObject) keeps the name, so the new file cannot be created first; instead the original is moved aside to a hidden name (`-old-`) and deleted when done (restored on failure). Whether a file already exists is taken from what the queue saw at planning time (find the handle in the path cache and confirm by name); the folder listing is not read per file (doing so would read the listing twice per file, N×M for uploads into folders of thousands of files). Leftovers from interrupted work are cleaned up from the listing read at planning time: `-part` is deleted; `-old-` is deleted if the new file is in place, otherwise restored to the original name (it is then the only copy). If a folder has that name, it is left alone. Names moved aside during an on-device move (`.name.xfer-move-<value>`) are restored to the original name, or to "name (1)" if that name exists (the name the move would have given). Limit: `.xfer-old-<value>` and `.xfer-move-<value>`, used when the name is too long to embed the original, are not cleaned up and remain hidden. Cleanup happens only when a transfer into that folder is planned |
| M14 | CopyObject: **folders fail (`0x2002`)**; copying to the same folder under the same name acts like overwriting the original (only the modification date changes), and renaming via the returned handle gives `0x2009` | Measured (Lenovo Tab P11) | Fixed: CopyObject only for copies to a different folder under the same name. Folders: create the folder + copy item by item. Copies that change the name go through a temporary file on the Mac (deleted right away). The returned handle is not used (G5) |
| M15 | MoveObject keeps the name → if the target folder has the same name (even one about to be renamed), it fails with `0x2002`. Works for folders and to the storage top level (parent 0) | Measured (Lenovo Tab P11) | Workaround: for a move that changes the name, if the target has the original name, first rename in place to a temporary name, then move |
| M16 | Zero storages: when the screen is locked or file transfer is not allowed, and briefly **right after plugging in**. AOSP MtpService adds storages only in `USB_DATA_UNLOCKED` | AOSP UsbDeviceManager/MtpService, libmtp README, measured (Galaxy Z Flip5) | Fixed: on zero, retry for a while (6 s); only if it stays zero, tell the user to unlock and choose File transfer |
| M17 | If the host does not read the event (interrupt IN) pipe, the phone's MTP server waits up to 1 s per event (object added, deleted, …) (logcat `Mtp send event failed: Timer expired`). The next command is delayed meanwhile, so one SendObject takes about 1.05 s (even for a 1-byte file), and when they overlap, receiving the file fails with `EBUSY` and SendObject returns `0x2002`. With libmtp too, the application must read events (`LIBMTP_Read_Event`) | Measured (occurs on two Lenovo Tab P11 units. Galaxy Z Flip5 does not wait even when events are not read: 300 uploads + listing take 8 s either way, no event-timeout log. Same on Teclast T65Max: 35.8 s vs 34.8 s) | Fixed: while the session is open, a read is always pending on the event pipe and events are discarded (listings are always fetched fresh, so events are not used). 300 uploads + listing: about 45 s instead of about 6 min; one upload about 0.1 s instead of about 1 s |
| M18 | Some devices keep the date of uploaded files; others replace it with the upload time (G6) | Measured | Verified: on the first upload, probe with a 1-byte hidden file (`probeKeepsUploadDates`) and remember the result per device and connection type. For devices that do not keep dates, compare by size and offer sending as a zip |
| M19 | Handles the client gets for objects it just created (copies, uploads, new folders) cannot be trusted as is (G5) | Measured | Defensive: rename or delete through such a handle only after GetObjectInfo confirms the name |
| M20 | If the same folder has an object of the same name, SendObjectInfo is refused with `0x2002` (no new object is created). Renaming also fails if the name exists | Measured (Lenovo Tab P11, Teclast) | Relied on: an upload planned as a "new file" whose name has appeared in the meantime reports "already exists" instead of overwriting (checked only after the refusal or failed rename) |

## G. Galaxy (Samsung MTP)

| ID | Behavior | Source | Handling |
|---|---|---|---|
| G1 | The vendor extension has no `android.com` (`microsoft.com: 1.0; samsung.com/kies: 6.0; samsung.com/devicestatus: …`) → not covered by libmtp's automatic Android flags | Measured | Fixed: the extension string is not used to decide whether a device is Android |
| G2 | `samsung.com/devicestatus`: no official documentation. **4 = charging only** (zero storages), 0 = file transfer | Research + measured (Galaxy Z Flip5) | Fixed: 4 → tell the user the device is set to charging only. The value while locked in file transfer mode has not been measured |
| G3 | libmtp's PID distinction (`6860` = MTP only, `685c` = MTP+ADB) does not match current devices | Measured (Galaxy S23, Android 16) | Fixed: decide from the interface list |
| G4 | Right after taking over from ptpcamerad, GetStorageInfo returns `0x2003` (Session Not Open), and 80 of 99 root GetObjectHandles return `0x2009` (item no longer exists) | Measured (Galaxy Z Flip5) | Defensive: on `0x2003`, reopen the session and retry once; skip items that no longer exist |
| G5 | **The new handle in a CopyObject response points not at the copy but at another file on the phone** (an unrelated photo). The copy on disk is correct | Measured (Galaxy Z Flip5, Android 16) | Workaround: use the returned handle only if it is the copy (name and folder); otherwise discard it — the copy is looked up by path later when needed (M19). Re-reading the target folder after every copy instead would make copying a whole folder quadratic in the number of files |
| G6 | Uploaded files get the upload time as their date, and SetObjectPropValue (DateModified) returns `0xA80A` (property not supported). Over ADB dates are preserved | Measured (Galaxy Z Flip5, Galaxy S10 5G) | Restricted: `keepsUploadDates = false`; compare by size. When dates matter, use ADB or send as a zip (G7) |
| G7 | Samsung My Files extracts zip but not tar. Extracting a zip **restores file dates to the second from the extended timestamp (0x5455)**; folder dates are not restored regardless of entry order; an extra folder named after the zip is created | Measured (Galaxy Z Flip5, extracted in My Files) | Workaround: "send as a zip". For a single folder, the zip is named after it and holds only its contents, so extracting gives the same structure. Folder dates are a limitation |
| G8 | A Galaxy Z Flip5 attached at 5 Gbps (USB 3) had its USB link drop and come back 5 times in 36 s (kernel: "link change interrupt", "hardware connection lost"). Each time it comes back, ptpcamerad grabs it first, so reconnecting takes 10–50 s | Measured (Galaxy Z Flip5) | Inform: if the device drops and immediately returns 3 or more times within 2 minutes, a ⚠ appears at the end of its row (hover: "USB keeps dropping" + advice on cable, port and hub; also in the connection panel). Not counted: reconnects within 15 s of plugging in, and reconnects caused by a USB mode change (product ID or MTP/ADB configuration changes) — the phone reconnects several times on its own (on Lenovo Tab P11, switching mode twice would otherwise trigger the warning). The threshold is 3, not 2, because a Galaxy switching between charging and file transfer reconnects with the same interfaces, indistinguishable from a drop (switching twice in 2 minutes is common) |
| G9 | Samsung My Files extracts Zip64: a small Zip64 zip, and a 4.4 GB zip made by the app's send-as-zip (a 4.4 GB file + a small file). Extracted sizes and contents match, and file dates are restored to the second (0x5455). `unzip -t` on the phone also passes | Measured (Galaxy Z Flip5, Android 16, transferred over ADB) | Fixed: when send-as-zip exceeds 4 GB, a single Zip64 archive (`ZipWriter`, Zip64 only for the values that exceed the limit) |
| G10 | DeleteObject on a file right after it was uploaded (sent under a temporary name and renamed) **sometimes reports success but the file remains** (it shows again on a new connection). SendObjectInfo or a rename to that name then fails with `0x2002`. In devtest "upload as planned", replacing with direct writes, about 5 of 15 runs. An experiment that sends only the same sequence of MTP commands (`sferry mtp-reuse-name`) did not reproduce it in over 30 runs | Measured (Galaxy S23, Android 16) | Defensive: if a freed name is refused, fetch the folder's name list once, delete the file with that name again, and retry (`MtpTuning.freedNameWait`). If the retry does delete the remaining original and then sending the new file still fails, the original is lost (the same risk the user is told about when enabling direct writes for replacements). For normal replacements, the delete is repeated only if this step deleted the original itself. The retry path has not been exercised on a device: the condition did not occur in 30 runs with it in place |
| G11 | **A file renamed inside a hidden folder (name starting with `.`)** (the last step of an upload is also a rename): if that folder is then renamed to a visible name on the same connection, GetObjectPropList (ObjectFileName) returns the **name before the rename** (`.xfer-part-…`). 1–4 of 5 files, and it stays that way after several seconds. GetObjectInfo gives the current name; the disk and a new connection are correct. Visible folder → hidden → visible (case-only rename, moving onto an overlapping name) does not trigger it. Without a check, cleanup (`tidyLeftovers`) takes such a file for an interrupted upload and **deletes the real file** (observed in a test folder) | Measured (Galaxy Z Fold4, Android 15) | Defensive: listing entries with work names (`WorkNames.isWorkFile`) and entries deleted by name (the G10 retry) have their name confirmed with GetObjectInfo. devtest "rename: a hidden folder made visible…" (fails 3 of 3 without the check) |

## H. macOS

| ID | Behavior | Source | Handling |
|---|---|---|---|
| H1 | The MTP interface appears as PTP class (6/1/1), so `ptpcamerad` grabs it as soon as the device connects. When the phone is plugged in, Photos (including its widgets) asks ptpcamerad for the photo list, and even after cleanup the phone keeps processing that query, so the first listing takes 17 s (normally 0.3 s) | Measured (macOS 26, Galaxy Z Flip5, ptpcamerad log) | Defensive: grab the interface as soon as the connect notification arrives; after cleanup, show why the app is waiting (`FSActivity.finishingEarlierRequest`); offer turning off the photo service in Settings |

| H4 | Which process holds an interface can be read from ioreg's `IOUserClientCreator` ("pid N, name"). MTP and ADB are different interfaces and can be used at the same time | Measured (Galaxy S23) | Fixed: "In use by another app" in the connection checklist, with a quit button |
| H5 | The USB device cannot be reset from the Mac: the macOS driver (AppleUSBCDCCompositeDevice) owns the device exclusively | Measured (Lenovo Tab P11) | Fixed: the M11 approach instead of a reset |
| H6 | A 6/1/1 device whose interface is not named "MTP" may be a camera | Defensive | Defensive: only interfaces named "MTP" are treated as phones (so cameras are not taken over) |

Storage is much faster than USB 3 (about 400–450 MB/s in practice), so USB is the ceiling. ADB matches or beats standard adb but stays below the USB limit (apparently on the phone's adbd side). MTP download improves slightly with 32 MB chunks (about 200–210 MB/s), and growing the Mac read buffer from 2 MB to 8 or 16 MB makes it slower (130–160 MB/s) → the limit appears to be a fixed per-chunk cost (about 9 ms) and the phone MTP server's read speed, not the Mac-side buffer (unconfirmed).

**MTP download chunk size (Galaxy S23, USB 3, 1 GB)**: per chunk size 4 MB 173, 8 MB 185–195, 16 MB 197–209, 32 MB 208–214, 64 MB 217–219 MB/s → the phone streams at about 223 MB/s with about 6 ms added per request. With chunks of 0.2 s worth (8–64 MB), a download alone takes 4.4/4.0/3.8 s for 1 GB instead of 5.8/5.1/4.8 s (alternating runs). But a folder listing during the download (3–4 requests) grows from 170 ms to about 580 ms → the app uses 8 MB chunks if there was browsing in the last second and large chunks otherwise: listings while browsing take 166–178 ms (worst 230 ms), the same as without a download (`sferry mtpfs browse-during`). On USB 2 (same Galaxy S23, 480 Mbps), a download alone takes 7.4–7.6 s for 300 MB (about 40 MB/s, the link limit), so chunks stay at 8 MB. But an 8 MB chunk then takes 0.2 s, and the median listing during a download is 658 ms → while browsing, chunks are also limited to 0.05 s worth (1–8 MB; about 2 MB on USB 2): median listing 159–160 ms (worst 316 ms).
